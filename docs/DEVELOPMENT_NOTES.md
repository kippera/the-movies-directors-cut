## Architecture
- `shim/asfreader.c` — reader filter. Pins: audio first, video second. Video pin outputs RGB24 VIDEOINFOHEADER, audio PCM. Threads: demux + one per pin; queue caps VCAP 60 / ACAP 100; IMediaSeeking with a 100 ms duplicate-seek dedupe (quartz calls SetPositions on several pins). `DllGetClassObject` dispatches the writer CLSID to `writer_get_factory()`. Logs to `C:\asfreader.log`.
- `shim/asfwriter.c` — writer filter. `IConfigAsfWriter::ConfigureFilterUsingProfile`, `IFileSinkFilter`, input pins accept RGB24/RGB32 and PCM16. Encodes `wmv2` + `wmav2`, sws to yuv420p, audio FIFO, finalises on stop/EOS and sends `EC_COMPLETE`.
- `shim/wmvcore.c` + `shim/wmprofile.c` — `wmvcore.dll` (IWMSyncReader on ffmpeg, IWMProfileManager/IWMProfile/IWMStreamConfig/IWMVideoMediaProps). The game loads it itself by name (`WMVCore.DLL`) and uses the profile manager to parse `Data\Video\WMVProfile_<Upload|Small|Medium|High|Best>_NA.prx`. Logs to `C:\wmvcore.log`.
- Static i686 ffmpeg n6.1.1, LGPL, configured by `ff/build.sh` (WMV1/2/3, VC1, WMA decoders; wmv2/wmv1/wmav2/wmav1 encoders; asf demuxer/muxer; x86asm disabled).

## Gotchas learned
- Playback is DirectShow, not the WMF sync reader. Wine builtins importing wmvcore (e.g. qasf) ignore the native override, so the reader was replaced by CLSID instead.
- The game's graph holds its own "The Movies Texture Renderer Filter", accepting RGB24 only.
- Export corruption (stripes) was fixed by SWS_ACCURATE_RND|SWS_BITEXACT in sws and `-mstackrealign`; do not drop them without re-testing with `wharness`.
- NEVER run `compatibilitytools.d/*/proton` with a glob: a wrong Proton rewrites the prefix `version` file (it was reset to `GE-Proton10-33` after one such mistake).
- Proton logging: `PROTON_LOG=1 PROTON_LOG_DIR=/tmp/movielogs`; add `WINEDEBUG=+loaddll,err+all` for DLL load decisions.

## Session 2 findings (audio-on crash investigation, 2026-10-25)
- **`_NA` = "No Audio".** `MoviesSE.exe` 0xa2f770 builds `Data\Video\WMVProfile_<Best|High|Medium|Small|Upload>[_NA].prx`; `_NA` is appended when the audio flag (`this+0x820`) is 0. So the earlier video-only export simply had audio off. With audio on, the game asks for the non-`_NA` profile (audio stream #1 WMA2 tag 0x161 44.1k stereo + video stream #2).
- Profiles live compressed (16-byte header + zlib) in `Data/pak/MISC0000.pak` and `Addon_2704_0001.pak`; `re/pakx.py <pak> <outdir>` extracts them. Audio bitrates: Best 192k, High/Medium 96k, Small 48k, Upload 20k. Also `wmvprofile_audio.prx` (audio only).
- **Audio export is two-stage** (graph code around 0xa2ed00-0xa2fd60): (1) audio-only graph `Movies Audio Source -> Wave Dest -> File Writer` renders `%sTMP%04d.wav` (game-internal filters + Wine File Writer; our DLLs not involved); (2) final graph `Video Source` + `File Reader for WAV` (AsyncReader, `this+0x878`) -> `Wav Parser` (`+0x87c`) -> `Audio Enc` (`+0x874`) -> `ASF Enc/Writer` (ours, `+0x880`). `Audio Enc` is found by 0xa2f920: if `IsDebuggerPresent()==1` it CoCreates the ACM wrapper, otherwise it enumerates CLSID_AudioCompressorCategory by friendly name stored at `this+0x620` (not yet identified; a failed lookup is a candidate failure/crash point under Wine).
- `shim/pharness.c` (reader -> writer with any real profile XML) reproduces nothing for Best: 192k audio + 8 Mbps/768x432 video encodes fine offline.
- **Real bug found offline:** profiles with audio < 24 kbps (Upload = 20k) make `avcodec_open2(wmav2)` fail ("bitrate too low"), `begin_encode` returns -1, no file is written and the graph never completes. Fix: clamp audio bitrate to >= 24000 (or higher) in `begin_encode`.
- The crash run left NO trace in `C:\asfreader.log` / `C:\wmvcore.log` (both flush per line), i.e. the game died before `WMCreateProfileManager`/writer creation, most likely in stage 1 or in the `Audio Enc` setup. Need a Proton crash log (see below) to confirm.
- Log to capture: Steam launch option `PROTON_LOG=1 PROTON_LOG_DIR=/tmp/movielogs WINEDEBUG=err+all,fixme+all,+loaddll,+seh WINEDLLOVERRIDES="*wmvcore=n,b" %command%`, then export with audio on / Best and look for `Unhandled exception` + backtrace.

## Session 2 fix: audio export freeze (root cause found)
- Freeze (black screen after choosing the profile) = stage-1 temp WAV (`C:\users\steamuser\AppData\Local\Temp\The Movies\TMP0000.wav`) had a zeroed RIFF header. The game's `Wave Dest` (0xaa66d0, a copy of the DirectShow WavDest sample) does `QueryInterface(IID_IStream)` on the downstream File Writer pin, then `Seek(0)`+`Write(46-byte header)`. Wine's built-in File Writer has no IStream, so the header was never written and stage 2 (`File Reader for WAV` -> `Wav Parser`) could not run.
- Fix: `shim/filewriter.c` = our own CLSID_FileWriter `{8596E5F0-0DA5-11D0-BD21-00A0C911CE86}` (input pin with IMemInputPin + IStream, sequential Receive writes, separate stream position, EC_COMPLETE on EOS), dispatched from `DllGetClassObject` and registered via a third `comClass` in `MoviesSE.exe.manifest`. Unit test: `shim/fwtest.c`.
- Also fixed: audio < 24 kbps (Upload profile = 20k) clamped to 32 kbps in `asfwriter.c` (was: wmav2 open failed, export hung).
- Build changes on this machine: `ff/build.sh` now passes `--disable-pthreads --enable-w32threads`; the DLL must be linked with `-static` (this toolchain is UCRT/posix-threads and otherwise imports libwinpthread-1.dll, which the game prefix lacks). Add `filewriter.c` to the asfreader.dll source list and `-static` to its gcc line.
- Backups of the previously deployed files are in the game dir: `asfreader.dll.bak-session1`, `MoviesSE.exe.manifest.bak-session1`.
- UNVERIFIED in-game: after the header is fixed the remaining stage-2 pieces are the Wine quartz Wav Parser and the `Audio Enc` lookup (0xa2f920, audio compressor by friendly name at `this+0x620`). If it still fails there, check `C:\asfreader.log` for `FileWriter ...` lines and the Proton log.

## Session 2 fix #2: export bounced back to the export screen ("Audio Enc" lookup)
- With the WAV header fixed, stage 2 created our writer, then silently aborted (writer destroyed before ConfigureFilterUsingProfile, wmvcore.log untouched). Cause: `0xa2f920` looks up the audio compressor by FriendlyName (default `Microsoft ADPCM`, set at 0xa2b86d; video default `DivX`) in `CLSID_AudioCompressorCategory` via `CLSID_SystemDeviceEnum`; Wine's category is empty.
- Fix: `shim/devenum.c` overrides `CLSID_SystemDeviceEnum` `{62BE5D10-...}` (manifest comClass -> asfreader.dll). Audio compressor category = one moniker "Microsoft ADPCM" (property bag FriendlyName/CLSID, BindToObject gives our "Audio Enc" PCM pass-through filter: input pin accepts PCM, output pin connects to the ASF writer and forwards the same IMediaSample). Every other category is forwarded to Wine's builtin devenum.dll (loaded by system dir path).
- Tests (Wine, throwaway prefix): `shim/devenum_test.c` (+manifest), `shim/aetest.c` (synthetic PCM -> Audio Enc -> writer -> valid wmav2 file), `shim/chaintest.c` (full AsyncReader -> Wav Parser -> Audio Enc -> writer; cannot run on this machine's system Wine because its GStreamer lacks wavparse, and not on GE-Proton outside Steam's runtime).
- UNVERIFIED in-game: Wine's `Wav Parser` (GStreamer based) under Proton, and the game's Connect() calls between File Reader -> Wav Parser -> Audio Enc -> writer. Our log shows `AudioEnc ...` lines for each step. The game's temp WAV header declares data size 46 bytes too large (header sample counted as data); harmless on Windows, hopefully on Wine.

## Text-descent performance fix (2026-10-30)
- Symptom: with `TextDescent=1` the studio and fullscreen menus dropped to 30-60 fps. Profiling build (per-stage QPC counters, logged as "mk_draw breakdown" every 300 frames) showed the glyph-quad loop costing up to 3.8 s per 300 frames.
- Cause: `getf()` calls `GetPrivateProfileStringA`, i.e. re-reads the ini FROM DISK on every call, and the quad loop called `getf("TextDebug")` per large glyph quad. Rule: never call `getf()` in a per-draw / per-quad path; read it once in the config reload (`cfg_textdebug`, `cfg_mrtcpu` now cached there; the movie-viewer path also read `MrtCPU` per small draw).
- Also added: per-glyph tail-row cache (`mk_tail_rows_c`, direct-mapped 16k entries, ~100% hits) and a per-texture-pointer width cache (`tex_w_cached`, refreshed every 300 frames) so each draw does one GetTexture. Output is identical.
- Result: quads 7-19 ms per 300 frames; screens at 100-144 fps. Remaining cost is `vblock` (reading the game's VB, ~1 s per 300 frames busy studio, 3-4 ms/frame); next target only if needed.
- Profiling counters (`MKT`, `g_mkt`) are still in the build and log (cheap). Snapshots: `gfx/d3d9.dll.textfix2` (deployed, md5 3ebbc4e872bb), `gfx/d3d9.dll.pre_textcache` (before), source backup `gfx/d3d9proxy.c.pre_textcache`.
